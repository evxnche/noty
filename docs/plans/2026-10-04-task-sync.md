# Noty Task Sync Implementation Plan

**Goal:** Share checkbox tasks between the current native Noty app and a private mobile webpage. Leave ESP32 code, deployments, and hardware untouched.

**Architecture:** Keep encrypted local notes authoritative for native editing. Extract only non-empty checkbox lines into a persistent encrypted sync ledger. A separate authenticated HTTPS service stores task records and merges changes field by field against the caller's last synced base. The mobile page uses the same API and stores its pending changes locally for offline retry. No photos or non-task note body text are uploaded. Unnamed lists are called Tasks; only explicitly named note titles are shared.

**Tech Stack:** Existing Swift/AppKit/SwiftUI and CryptoKit; standard Node.js HTTP/crypto/filesystem APIs; dependency-free mobile HTML/CSS/JavaScript; Vercel functions and Upstash Redis REST for durable cloud storage, if a free plan with automatic upgrades disabled is available.

## Contract

A task is `{id, noteId, listTitle, text, completed, position, deleted, version}`. IDs and note IDs are UUID strings; text is at most 2000 UTF-16 units, listTitle at most 120; position is a finite number; version is a nonnegative integer maintained by the server. Tasks removed from a note or archived become tombstones. Empty draft checkbox lines are not shared.

`GET /api/sync` returns `{tasks, conflicts: []}`. `POST /api/sync` accepts `{changes: [{task, base}]}`; base is the prior server task, or null for a new task. Returns `{tasks, conflicts: [{id, task}]}`. All operations require `Authorization: Bearer <NOTY_SYNC_TOKEN>` (32+ characters). A conflict applies no changes for that task. Different fields merge; a same-field edit against a different base reports a conflict. Identical retries are idempotent. Keep tombstones so an offline client cannot resurrect a deleted task.

The browser keeps a base and a desired task for each pending change, replaces both only after acknowledgement, and shows conflicts with actions to keep the local edit or take the server version. Native preserves conflicting text as an additional task and adopts the remote version. Changes during an in-flight request remain pending against the returned base.

## 1. Native ledger and tests

Create `Sources/TaskSyncModel.swift` with wire types, extraction, stable task matching, and remote application preserving unrelated note lines. Match unchanged task text before positional replacements, so inserted/reordered tasks preserve identity. Persist both desired records and their server bases encrypted with the existing AES key. Regression tests cover edits, reorders, duplicates, completed tasks, tombstones, remote insertion, and preservation of prose/photos.

## 2. Private sync service and tests

Create `web/api/sync.mjs`, `web/lib/sync.mjs`, a dependency-free local server, Node tests, and Vercel config. Validate requests and enforce authentication before accessing storage. Use Redis CAS via EVAL to prevent concurrent requests dropping each other's updates; use a persistent file adapter for local testing only. Test unauthorised requests, malformed/oversized input, concurrent edits, retries, field merging, deletes, and persistence. Fail closed if production storage is absent.

## 3. Mobile page

Create a restrained monochrome mobile task page under `web/public`, using the existing Noty mono fonts if practical. Provide connection, task creation, editing, completion, deletion, list choice, syncing/offline status, and conflict handling. Use textContent and DOM APIs for user text. Token pairing uses a URL fragment that is cleared immediately; do not send secrets in URLs or logs. Preserve in-flight edits and queued offline changes. Add a manifest and minimal service worker for the app shell, without caching API responses or credentials.

## 4. Native integration, deployment, verification

Add a native sync settings window with endpoint, private key, enable/disable, sync status, and a phone pairing link/QR. Hook note mutations into the ledger, poll at a bounded interval, debounce local pushes, and update open editors safely. Persist configuration with owner-only permissions and keep sync disabled if unconfigured. Build and run existing tests plus new sync tests, verify against the real HTTP service, exercise the mobile UI in a browser, and deploy a separate private project if free storage can be provisioned. Install the rebuilt native app with a backup of the current bundle and relaunch cleanly. Document the stable API for a future ESP32 integration without editing that project.

## Evidence boundaries

Preserve every existing uncommitted change. Do not commit unrelated work. Do not claim mobile hardware or ESP32 verification; those require the actual device. If cloud provisioning requires a user-owned account approval, finish local code and verification before asking for that specific missing action.
